# V0-M2 — Threads and shared state

## Goal

Run independent simulated sensors as threads inside one Linux process and
understand their lifecycle before adding synchronization primitives.

## Architecture

```text
main thread
  ├── speed sensor thread       ─┐
  ├── RPM sensor thread          ├── shared process memory
  └── temperature thread       ──┘
                ↓
             join()
                ↓
       main reads final state
```

Threads share the process heap and referenced objects, but each thread has its
own execution state and stack. The sensor functions update separate fields in
one shared state object. The main thread reads the final state only after all
threads have joined.

## Why synchronization is not here yet

The next milestone will demonstrate a true race condition and add a mutex. A
condition variable and producer-consumer queue will come later. Introducing
those now would hide the basic thread lifecycle this milestone is meant to
teach.

This implementation should not be treated as a general thread-safe shared
state design. It is a deliberately narrow learning step.

## Verification

1. Build the project with CMake.
2. Run the simulator several times and observe sensor-thread output.
3. Use GDB's `info threads` command while stopped in a sensor function.
4. Use `strace` to observe the process and thread-related system calls.

## Interview checkpoint

Before V0-M3, be able to explain:

- process versus thread;
- what memory threads share;
- why each thread has its own stack;
- why `join()` matters;
- why sleeping is not synchronization;
- why the current design is only a transitional learning example.
